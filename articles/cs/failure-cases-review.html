案例一：小红书账号被封

事件经过

2026-08-29 17:06–17:13，尝试自动发布漫庐"呼吸食材"系列小红书文案（v30–v34，共5篇）。

结果：全部触发"因违反社区规范禁止发笔记"拦截。账号被限制发布至 9月5日。

根因分析

不是文案内容本身的问题，而是系统自动推荐话题引入了敏感词：

推荐话题中包含：
- #邪修         ← 游戏/玄幻相关，触发内容安全审核
- #补气血养生howto  ← 中英混杂，疑似营销号特征
- 其他养生类标签   ← 批量发布+同类标签=机器人行为

反复提交加重了限制。系统在每次失败后继续尝试，形成恶性循环。

机制理解

平台行为我们的触发后果
自动推荐话题接受了系统推荐的tag敏感tag带入内容
频率检测7分钟内发布5篇触发风控
重复提交失败后继续尝试加重处罚
教训：自动化发布必须设置安全阀——敏感词过滤 + 频率限制 + 失败即停止。不能无限重试。

修复措施

  • 禁用系统自动推荐话题，改用预定义安全tag池
  • 发布间隔拉长到30分钟以上
  • 单次任务最多尝试2次，失败后人工介入
  • 当前处于冷静期，建议48小时后用安全tag重新测试

案例二：能力第二天丢失

现象描述

当天成功完成的操作（知乎发布、催眠器部署、记忆系统操作），第二天新会话中无法复现。

根因：opencode.db 不自动加载

opencode的新会话只自动加载 memory_blocks（persona/human/project等固定block），不会自动加载 opencode.db（全量历史消息）。

新会话启动时自动加载：
  ✅ persona.md      → 我的身份和行为规则
  ✅ human.md        → 用户画像
  ✅ project.md      → 项目信息
  ✅ USER.md         → 当前状态

新会话启动时不自动加载：
  ❌ opencode.db     → 45+会话的完整消息记录
  ❌ 昨天的TODO      → 未写入block的待办事项
  ❌ 临时决策        → 会话中产生的临时结论

为什么知乎能发而小红书不行？

这是一个会话内知识 vs 持久化知识的区别：

  • 知乎：在AGENTS.md和memory_blocks中有明确规则（"每篇间隔10分钟"），新会话能看到
  • 小红书发布脚本：保存在 /tmp 目录，是临时文件，新会话不知道它的存在
  • CDP浏览器连接：需要Edge进程以调试模式运行，新会话不会自动重建
修复：AGENTS.md顶部已添加强制规则——每次新会话第一步跑 memory_recover.py，列出最近会话让用户知道上次干了什么。

案例三：记忆保持机制分析

三层记忆的工作原理

第一层：memory_blocks（每次自动加载）

路径: ~/.opencode/memory_blocks/
包含: persona.md, human.md, project.md, USER.md 等
加载时机: 每次新会话启动时自动注入系统提示
特点: 内容精炼，但需要手动维护（写完要记得更新）

可靠但有限：block快满时需要压缩旧记录，压缩过程可能丢失细节。

第二层：opencode.db（永存但不自动加载）

路径: ~/.local/share/opencode/opencode.db
大小: ~4.76GB，45+会话
内容: 所有会话的完整消息记录
查询: python memory_recover.py
恢复: opencode --session <完整ID>

最可靠：杀进程/关机/重装都不丢。但需要主动查询，不会自动注入到新会话。

第三层：Memory Service（Git版本化独立库）

路径: ~/.memory-service/data/
机制: mb write <tag> <内容> 写入，每小时git commit
特点: 独立于opencode，evolve_daemon + EvolveGuard保活

结构化记忆：适合存储需要长期保存的重要结论（持仓、待办、项目进展）。

为什么"写记忆"这么重要

很多会话中的关键结论只存在于opencode.db的消息记录里，没有写入memory_blocks或Memory Service。第二天新会话启动时，这些结论不可见。

这就是为什么AGENTS.md强调：重要结果、持仓、待办必须当场写入memory block，不要等。

已验证的有效做法

做法效果来源
每次会话开始跑 memory_recover.py知道上次干了什么，100%准确AGENTS.md强制规则
重要结论写入选定block新会话自动加载，不依赖db日常实践
mb write tag 内容git版本化，可回溯Memory Service
opencode --session <ID> 恢复回到精确的对话状态教过多次

无效做法（已废弃）

  • Supermemory（ASMR）：从未成功运行过——无API key、数据全空、唯一一次调用即报错（2026-08-03调查结论）
  • 依赖opencode.db自动加载：设计上不支持，不要指望

案例四：外贸研究搜索失败

现象

2026-08-29 21:22–21:54，尝试为秦奕生成"外国企业进口中国准入方向"分析报告时，所有网络搜索均失败：

  • DuckDuckGo: TimeoutException after 30s
  • Bing CN: 返回空结果（解析失败）
  • customs.gov.cn: SSL证书验证失败 + 连接超时
  • MOFCOM: 404

根因

WSL的網絡環境不穩定，DNS解析和SSL握手频繁失败。这与我们在Linux环境的网络配置有关，与Agent架构本身无关。

应对方案

当网络搜索不可用时，基于已有知识（2024-2025年政策知识）+ 刘思毅文章框架生成报告。虽不如实时搜索准确，但核心结论（负面清单缩减、RCEP关税减免、自贸区通道）与公开政策一致。

教训：Agent的搜索能力依赖底层网络环境。需要在架构层面增加搜索降级策略——DDG超时 → Bing → 本地知识库 → 纯知识生成。

总结：三个核心教训

  1. 自动化必须有安全阀——小红书封号是因为没有失败停止机制和敏感词过滤
  2. 知识必须显式持久化——会话内的知识不会自动带入新会话，必须写入block或Memory Service
  3. 搜索能力不稳定——网络层问题导致搜索经常超时，需要降级策略和本地知识兜底
