Agent架构复盘：Hermes + opencode

单网关多会话转发设计，含踩坑记录与记忆保持机制

2026-08-30 | Agent架构复盘 | 8分钟阅读

架构总览

当前系统由两层构成：Hermes Gateway（WSL内运行）作为消息路由层，opencode（Windows原生）作为实际执行层。

飞书用户
    ↓
Hermes Gateway (:18789)        ← WSL，处理平台接入
    ↓ opencode-bridge插件
opencode session               ← Windows，实际执行AI任务
    ↓
Agnes AI API (apihub.agnes-ai.cn)
    └── agnes-2.5-flash (200k上下文)
    └── agnes-2.0-flash (128k，备用)

关键设计决策：网关与执行分离。Hermes负责飞书WebSocket连接和消息路由，opencode负责LLM调用和工具执行。两者通过 opencode-bridge 插件通信，HTTP 204无内容转发。

核心组件

1. Hermes Gateway

运行在WSL（Ubuntu）内，监听 :18789。核心职责：

  • 飞书平台WebSocket长连接（reconnect_interval: 30s）
  • 消息路由：按 chat_id 分发到对应opencode session
  • Agent缓存管理：idle-TTL超时后驱逐（约60分钟）
  • 压缩代理：超过阈值时自动压缩历史消息

日志中的关键模式（2026-08-29实测）：

# 正常转发
opencode-bridge: forwarded to session ses_fdb3a6c3bffev4gD8anHRtv0gu (HTTP 204)

# 缓存驱逐
Agent cache idle-TTL evict: session=agent:main:feishu:dm:... (idle=3737s)

# 压缩触发（420条消息，~121k tokens → 压缩到304条，~69k tokens）
Session hygiene: 420 messages, ~120,920 tokens — auto-compressing
Session hygiene: compressed 420 → 304 msgs, ~120,920 → ~68,987 tokens

2. opencode 执行层

运行在Windows原生环境，实际执行LLM调用和工具。配置要点：

{
  "model": {"default": "agnes-2.5-flash", "provider": "agnes"},
  "mcp": {"codebase-memory-mcp": {
    "command": ["/root/.local/bin/codebase-memory-mcp"],
    "type": "local"
  }},
  "compression": {
    "enabled": true,
    "threshold": 0.5,
    "target_ratio": 0.2,
    "protect_last_n": 20
  }
}

关键参数：

  • compaction.enabled：已设为 false（2026-08-20修复死循环问题）
  • compression.threshold：50%上下文时触发
  • compression.protect_last_n：最后20条消息不压缩

3. 三层记忆系统

层级路径自动加载可靠性说明
1. memory_blocks ~/.opencode/memory_blocks/ ✅ 每次新会话 高 persona/human/project等block，自动注入
2. opencode.db ~/.local/share/opencode/opencode.db ❌ 不自动加载 极高（永存） 全量原始消息，杀进程/关机不丢
3. Memory Service ~/.memory-service/data/ ❌ 需手动mb 高（git版本化） 独立git库，evolve_daemon每小时提交

关键教训：新会话只自动加载memory_blocks，不自动加载opencode.db。AGENTS.md顶部的强制规则——每次新会话第一步跑 memory_recover.py——就是为了弥合这个gap。

踩坑记录

坑1：compaction死循环（2026-08-20）

现象：build agent和opencode内置compaction相互触发，形成 build → compaction → build → ... 无限循环。

误判：以为是OMO(oh-my-openagent)插件导致，其实OMO已在前一天禁用。

根因：两个compaction机制都没有可靠的终止条件。

修复：compaction.enabled = false，唯一需要的修复。

预防：监控日志大小，发现异常增长立即终止进程。

坑2：FTS写入延迟导致上下文不一致

日志警告：Persisted transcript lagged live cached history (disk=375, memory=377)

含义：磁盘持久化的消息数落后于内存缓存，系统选择保留内存中的live context。长期运行可能积累不一致。

当前影响：无明显故障，但需关注。建议定期重启gateway清理状态。

坑3：Feishu网络不可达

错误：HTTPSConnectionPool(host='open.feishu.cn', port=443): Network is unreachable

根因：WSL的网络栈与Windows宿主隔离，某些网络变更后WSL DNS失效。

修复：重启WSL（wsl --terminate + 重新启动）。

预防：gateway配置了 reconnect_interval: 30，但DNS问题需要手动干预。

坑4：浏览器CDP断连

现象：Edge进程存在，但端口9222未监听，CDP连接失败。

根因：Edge重启后调试端口不自动启用。

修复：需手动重启Edge并添加 --remote-debugging-port=9222 参数。

设计选择与权衡

选择方案A方案B为什么选B
网关位置 Windows原生运行 WSL运行 WSL有完整的Unix工具链，Python环境更干净，与Hermes官方文档一致
记忆持久化 只靠memory_blocks 三层架构 单靠blocks不够（内容有限），单靠db不够（不自动加载），三层互补
压缩策略 关闭压缩 50%阈值+保护最后20条 关闭会导致OOM，保护最后20条确保关键对话不丢失
多Agent隔离 共享同一workspace 每个Agent独立workspace 记忆和技能完全隔离，避免污染

运维清单

  • 每日检查：gateway.log确认飞书连接正常（无Network is unreachable）
  • 每周检查：opencode.db大小，发现异常增长立即处理
  • 每次新会话：先跑 memory_recover.py 恢复上下文
  • 每月检查：Memory Service git log确认evolve_daemon正常提交
  • 浏览器更新后：验证CDP端口9222是否重新监听
